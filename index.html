00 / Abstract

Question → method → result.

Question.

Which content items should an editor review first when the goal is to identify pages showing a measured decline signal?

Method.

The analysis compares a transparent editorial rule with a deliberately conservative machine-learning ranking using leakage-screened content, visibility, freshness, position, and query-level features, with client-held-out evaluation.

Result.

The final leakage-clean model reached an AUC of 0.615, while the transparent baseline remained stronger at the highest Precision@K levels in the reported test split.

Interpretation.

The model is therefore best understood as a complementary discovery queue: it surfaces a materially different population rather than replacing the trusted baseline.

01 / Introduction & problem statement

What should an editor review first?

FlyRank editors face a large number of content items with different levels of visibility, freshness, search position, and query behavior. The system turns these signals into a ranked review queue.

The decision supported by this work is prioritization: which pages deserve human attention first. A recommendation is a review prompt, not an automatic editorial action.

“The system ranks opportunities for attention; it does not decide what should be edited.”

03 / Methodology

A deliberately conservative modeling design.

Assumptions

The model is treated as a ranking aid, not a causal estimator. A higher score means the model places an item earlier in the review queue; it does not mean that refreshing the page will cause a future improvement.

Final feature set

impressions_prev30
avg_position_prev30
days_since_last_update
query_impressions_prev30
query_concentration_prev30

Label definition

The project pipeline defines the bootstrap decline label as is_declining_label = (trend_direction == "down"). Precision@K therefore measures how well the ranking surfaces pages carrying this observed decline flag. It should not be interpreted as validation of a causal “refresh will improve traffic” claim.

Baseline

The baseline is a transparent editorial rule based on visibility, freshness, and position. In the action-playbook implementation, the rule flags visible pages that are stale or have weaker-than-median position, with plain-language reason codes such as stale_but_visible, weak_position, and low_signal.

Validation design and leakage checks

Client identity is treated as a grouping variable rather than a model feature. The project work also uses grouped validation so that client pages do not simply appear on both sides of a validation fold. The leakage audit removed label-derived fields and excluded suspect query features from the final configuration, even when those features produced stronger diagnostic AUC.

Leakage rule: a feature is not retained merely because it improves a metric. If it is derived from the target, from future information, or otherwise violates the decision-time information boundary, it is excluded.

07 / Ranked recommendations

Use the model as a second layer, not a replacement.

1

Baseline queue

Keep the transparent rule as the primary high-visibility review queue because it has the strongest reported Precision@K.

2

Model discovery queue

Use model rankings to discover lower-traffic content that the baseline does not prioritize.

3

Disagreement review

Investigate cases where the model and rule strongly disagree. Either system can be right; disagreement is a useful review signal.

4

Human verification

Treat every score as a review prompt. Do not automatically edit, publish, remove, or guarantee outcomes from the score alone.

08 / Limitations & honest framing

Useful evidence, not a causal claim.

Confidence is moderate for using the system as a screening and prioritization aid within this dataset. Confidence is lower for generalizing to future periods or unseen clients without additional validation.

The main limitation is straightforward: the final model does not outperform the baseline on Precision@K.

The target is an observed decline flag, not a direct measurement of whether a refresh would improve business outcomes. The model therefore supports prioritization, not a claim that a recommended intervention will cause traffic growth.

Before production use, validation should include additional clients, future time periods, editor acceptance, and measurement of whether recommended refreshes actually improve outcomes.

Observed relationships → directional ranking → human decision support.

11 / Conclusion

A complementary system is the strongest result.

The baseline provides the trusted high-visibility queue. The model provides an additional discovery layer.

The experiment therefore supports a complementary workflow rather than replacing the transparent rule with machine learning.
